# Soundiiz バックエンド仕様(HAR解析結果・機密情報除去済み)

HARから抽出した実際のAPI構造。認証トークン・Cookie・個人メールアドレス等は全て除去済み。
bolt.newに「これを参考に実装して」と渡すためのリファレンス。

## 全体アーキテクチャ

- ベース: `https://soundiiz.com/v1/`
- 2系統のAPIが混在
  - `/v1/webapi/*` — 旧来のWeb UI向けAPI(変換実行、スケジュールタスクCRUDなど)
  - `/v1/api/*` — 新しめのREST風API(プラットフォーム別のplaylist/track取得、マッチング)
- レスポンス形式は概ね `{"data": ...}` ラップ(一部素の配列を返すエンドポイントもある。`webapi/me` のように `data` ラップ無しで直接オブジェクトを返すものもある)
- リクエストヘッダ: `Content-Type: application/json`, `X-Requested-With: XMLHttpRequest`(AJAX判定用), **`X-CSRF-Token`**(状態変更系リクエストで送られる)
- **認証方式**: リクエストに `Authorization` ヘッダは無い。セッションCookie + CSRFトークン方式(このHARはCookie除去済みエクスポートのため生Cookieは含まれない)。加えて `GET /v1/webapi/me` のレスポンスに `auth_tokens.access_token`(`expires_in` 付き)が含まれており、モバイル/外部API用のBearerトークンも別途発行される設計。各音楽プラットフォームの認可(Spotify等のOAuth)はサーバ側が接続済み状態として保持する。
  - → bolt.newで実装するなら: セッション or JWT どちらでも良いが、**状態変更(convert/delete/matching/scheduledtask)はCSRFトークン必須**という前提を踏襲すると安全。

## コアのドメインモデル

### Track(曲)
プラットフォーム間で共通の正規化スキーマ:
```json
{
  "platform": "spotify",
  "type": "track",
  "id": "0mm4rVCT0ryEZNdOAV4i31",
  "title": "Skip Don't Play It",
  "artist": "BROSA",
  "artistLink": "https://open.spotify.com/artist/...",
  "album": "Skip Don't Play It",
  "albumLink": "https://open.spotify.com/album/...",
  "isrc": "NL8RL2669320",
  "bpm": null,
  "duration": "145",
  "trackLink": "https://open.spotify.com/track/...",
  "preview": "https://p.scdn.co/mp3-preview/...",
  "picture": "https://i.scdn.co/image/...",
  "addedDate": 1784458353,
  "playedDate": null,
  "addedBy": "username",
  "position": "1",
  "shareUrls": [],
  "isFound": null
}
```
→ **これが肝**。どのプラットフォームのトラックも同一スキーマに正規化して扱っている。isrc・title・artist・albumがマッチングのキーになる。お気に入り一覧(`/users/me/platforms/{platform}/tracks`)も変換履歴(`/history/playlistconvert/{id}/tracks`)も、**完全に同じTrackスキーマ**を返す。

### Album(アルバム)
Trackとは別スキーマ。**`upc` がアルバム版のマッチキー**(ISRCのアルバム相当)。`/users/me/platforms/{platform}/albums` が返す:
```json
{
  "platform": "spotify",
  "type": "album",
  "id": "...",
  "title": "...",
  "artist": "...",
  "artistLink": "...",
  "upc": "...",
  "releaseDate": "...",
  "duration": "...",
  "nbTracks": 12,
  "albumLink": "...",
  "picture": "...",
  "addedDate": 1784281358,
  "shareUrls": [],
  "isFound": null
}
```

### Artist(アーティスト)
これも別スキーマ。**キーは `title` ではなく `name`**、加えて `fans`/`bio`/`genres` を持つ。`/users/me/platforms/{platform}/artists` が返す:
```json
{
  "platform": "spotify",
  "type": "artist",
  "id": "...",
  "name": "...",
  "fans": 12345,
  "bio": "...",
  "genres": ["..."],
  "artistLink": "...",
  "picture": "...",
  "shareUrls": [],
  "isFound": null
}
```
→ Soundiizはプレイリストだけでなく **お気に入りトラック / アルバム / アーティストのライブラリ同期**も対応している。マッチングは track=isrc、album=upc、artist=name(+genres補助)と、種別ごとにキーが違う点に注意。

→ **レスポンスのポイント**:
- 各trackに `isFound: true/false` が付与される(destプラットフォームで見つかったか)。リクエスト時は全て `null`。
- `results.score` / `results.nbSource` = 見つかった曲数 / 元の曲数(例では 7/7 で全曲マッチ)。ここでマッチ率をユーザーに見せる。
- `results.id` = **dest側に新規作成されたプレイリストのID**(この例では Amazon Music の playlist ID)。convertは変換と同時にdestプレイリストの作成/書き込みまで一気にやる。
- `data: 1` は処理成功フラグ。

→ **変換フローの実装イメージ**:
1. srcプラットフォームからトラック一覧取得(正規化済みスキーマ)
2. `isrc` / `title`+`artist` でdestプラットフォームを検索
3. 見つからなければ `isFound: false` として保留 → ユーザーに手動マッチングさせる(`/v1/api/matching`)
4. 見つかった曲をdestのプレイリストに書き込み

## 自動同期(Scheduled Tasks)

### `POST /v1/webapi/automation/scheduledtask/add` の実リクエスト/レスポンス

プレイリストの片方から新規作成する例(Spotify → Navidromeで新規プレイリスト作成):
```json
// REQUEST
{
  "title": "[Spotify > Navidrome] Hype Machine Favorites Vol. 1",
```

## bolt.newに伝えるべき実装方針(要約)

1. **プラットフォームアダプタパターン**: 各音楽サービス(Spotify, Apple Music, YouTube Music, SoundCloud, Amazon Music, Last.fm, Navidrome, Bandcamp他 全66種)ごとに、共通インターフェース(`getPlaylists`, `getTracks`, `getAlbums`, `getArtists`, `writePlaylist`, `writeFavorites`, `searchTrack`)を実装するアダプタを用意。capability(`Pp Tt Aa Rr` の読み書き ×種別 + `maxTracksInPlaylist`)をプラットフォームごとに宣言し、変換元/先の選択肢バリデーションに使う(上のcapabilityマトリクス参照)。
2. **4種の正規化スキーマ**: **Track**(キー=isrc)/**Album**(キー=upc)/**Artist**(キー=name、フィールドは`title`でなく`name`)/**Playlist**。Trackスキーマはconvert/matching/track-add/resultFile/search全エンドポイントで完全に共通なので、これを1つの型として定義して使い回す。マッチは種別ごとにキーが違う(track=isrc、album=upc、artist=name+genres)。無ければtitle+artistのファジーマッチにフォールバック。
3. **変換パイプライン**: fetch source → normalize → match against dest (auto) → unmatched(`isFound:false`)分は `tracks/search?query="曲名 - アーティスト"` で候補提示 → ユーザー選択 → `POST /matching` 登録 → write to dest → 結果を `{elements[], score, nbSource, id(=新規destプレイリストID)}` で返す。
4. **手動マッチングの永続化**: 一度手動で紐付けたペア(source/dest)はDBに保存(`matchings`テーブル)、次回以降は自動適用。表記ゆれ(`M/A/R/R/S` vs `M|A|R|R|S`)はそのまま許容する設計。
5. **バッチ/履歴管理**: 変換ジョブを非同期実行し、進捗を `batches`(playlists/albums/artists/tracksを個別カウント、statut=4で完了)、実行ログを `scheduled_task_history`(start/end/statut/error)に記録。`current_batch_convert` をポーリングして進捗表示。
6. **スケジュールタスク**: cronベース定期実行。`method:18`(全置換)、`freqType`/`freqInterval`/`freqHour("HHMM")` で頻度、`actionCode`(idSrc/platformSrc/idDest/platformDest のJSON文字列)で対象を指定。`idDest:"newplaylist_soundiiz"` で新規作成。**空ボディPOSTで「今すぐ実行」**。作成上限は `max_scheduled_tasks`(プラン依存)。
7. **ユーザー/課金モデル**: `webapi/me` に倣い、プラン(`subscription_plan`/`status`)、クォータ(`max_scheduled_tasks` vs `nb_scheduled_task`)、通知購読(`notifications` 配列)、実行中バッチを1オブジェクトに集約。
8. **認証**: セッションCookie + `X-CSRF-Token`(状態変更系必須)。外部API用に `access_token`(`expires_in`付き)も発行する構成。プラットフォーム連携はサーバ側でOAuthトークンを保持。

---
※ 元HARファイルには認証トークン(`webapi/me`のaccess_token、リクエストのCSRFトークン)・メールアドレス・base64画像データ・mp3-previewのcid等の機密情報が含まれていたため、本ドキュメントでは全て `<REDACTED>`/`...` で伏字化しています。API構造・スキーマ・フィールド名は一切要約・省略していません。bolt.newに渡すのはこのファイルのみで十分です(元の32MB HARを送る必要はありません)。
